= Section 1.2 - Smart Alerts and Dual-Path Remediation
:navtitle: Smart Alerts and Dual-Path Remediation

*Estimated time: 25-35 minutes*

== Objective

In this section, we will configure a **Smart Alert** in Instana that detects when the Flask application stops responding. We'll create a webhook channel pointing to your Event-Driven Ansible listener, then simulate a service failure to watch the complete automated remediation workflow execute.

By the end of this module, you'll have a fully operational closed-loop AIOps system: Instana detects the problem → EDA is notified → AAP executes remediation → Service is restored → Alert auto-closes.

== Learning Objectives

After completing this module, you will be able to:

* Create a generic webhook alert channel in Instana
* Configure a Smart Alert for service-level monitoring
* Simulate a service failure and observe the detection
* Trigger automated remediation through Event-Driven Ansible
* Review the complete incident-to-resolution workflow in multiple tools
* Understand how observability platforms close the loop with automation

== Prerequisites

Before starting this module, ensure:

* You have access to the Instana UI (login credentials from Part 1)
* Your EDA webhook listener is running on the bastion (port 5000)
* The Flask web application (`lab-webapp-{guid}`) is running and receiving traffic
* You have access to Ansible Automation Platform (controller)

== Step 1: Get Your EDA Webhook URL

The EDA rulebook runs a webhook listener on port 5000 of your bastion VM. You need this URL to configure the alert channel in Instana.

Your EDA webhook URL is:

[source, text]
----
https://eda-webhook-{guid}.apps.{subdomain_base}
----

[NOTE]
====
This URL is automatically created when the lab deploys. The `{guid}` and `{subdomain_base}` variables are substituted by the lab provisioning system.
====

Save this URL. You will need it for the Instana alert channel configuration.

== Step 2: Create a Generic Webhook Alert Channel in Instana

An **alert channel** is where Instana sends notifications when alerts fire. We'll create a generic webhook channel that points to your EDA listener.

2. Click on **Settings** in the left navigation menu
3. Navigate to **Alerting** → **Alert Channels**

[start=4]
4. Click the blue **+ Add Alert Channel** button in the top right

image::instana_add_alert_channel.png[Add Alert Channel, link="_images/instana_add_alert_channel.png", window=blank]

[start=5]
5. Fill out the following fields:

[options="header"]
|===
| Field
| Value

| Alert Channel Type
| Generic Webhook

| Name
| `AIOps Automated Remediation - {guid}`

| Webhook URL
| `https://eda-webhook-{guid}.apps.{subdomain_base}`
|===

image::instana_webhook_channel_config.png[Webhook Channel Configuration, link="_images/instana_webhook_channel_config.png", window=blank]

[start=6]
6. Leave other fields at their defaults and click **Create**

[start=7]
7. You should see a success message: "Alert channel created successfully"

image::instana_webhook_channel_created.png[Webhook Channel Created, link="_images/instana_webhook_channel_created.png", window=blank]

[NOTE]
====
The webhook channel is now ready. Instana will POST the full alert payload (including the issue state and metrics) to your EDA webhook listener whenever an alert fires on this channel.
====

== Step 3: Create a Smart Alert for Your Service

A **Smart Alert** monitors a specific metric on your service and fires when anomalies are detected. We'll monitor the **Calls** metric (throughput) and alert when it drops below 1 call per minute, indicating the service is down.

=== In the Instana UI:

1. Click on **Services** in the left navigation menu
2. Search for and click on your service: `lab-webapp-{guid}`

image::instana_services_search.png[Services Search, link="_images/instana_services_search.png", window=blank]

[start=3]
3. Once in your service details, click on the **Analytics** tab

image::instana_service_analytics_tab.png[Analytics Tab, link="_images/instana_service_analytics_tab.png", window=blank]

[start=4]
4. Click on the **+ Add Alert** button (usually in the top right of the Analytics view)

image::instana_add_alert_button.png[Add Alert, link="_images/instana_add_alert_button.png", window=blank]

[start=5]
5. You'll see a Smart Alerts dialog. Fill out the following:

[options="header"]
|===
| Field
| Value

| Alert Name
| `{guid} Service Down - Calls Drop`

| Scope
| Your service: `lab-webapp-{guid}`

| Metric
| Calls

| Condition
| < 1 (less than 1 call per minute)

| Evaluation Granularity
| 1 minute

| Alert Channel
| Select: `AIOps Automated Remediation - {guid}`
|===

image::instana_smart_alert_config.png[Smart Alert Configuration, link="_images/instana_smart_alert_config.png", window=blank]

[start=6]
6. Review the configuration and click **Create Alert**

image::instana_alert_created.png[Alert Created, link="_images/instana_alert_created.png", window=blank]

You've successfully created your Smart Alert! When the service stops responding (calls drop below 1 per minute), Instana will send a webhook POST to your EDA listener.

[NOTE]
====
Smart Alerts are threshold-less and use machine learning to understand normal baseline behavior. However, in this demo, we've explicitly set the condition to `< 1` for clarity. Instana will fire the alert when calls drop below this threshold for approximately 1 minute.
====

== Exercise 1: NLP Matching - Observing Smart Recommendation

Before we break the service, let's manually test how Instana's NLP ranks your available job templates.

=== Triggering NLP Matching in Action Catalog

1. In Instana, navigate to **Action Catalog** (settings or explore menu)

image::instana_action_catalog.png[Action Catalog, link="_images/instana_action_catalog.png", window=blank]

[start=2]
2. You should see all available actions synced from AAP:
   * Type: ANSIBLE
   * Organization context: Instana AIOps
   * Names: Templates from your AAP org

image::instana_action_catalog_list.png[Action Catalog List, link="_images/instana_action_catalog_list.png", window=blank]

=== Understanding NLP Confidence Scoring

The Action Catalog displays **confidence scores** for how well each template matches a given incident:

[cols="1,3,2", options="header"]
|===
| Confidence
| Meaning
| Example

| **High (0.8+)**
| Strong semantic match to incident text
| "Restore Web App Service" matching "calls drop" alert

| **Medium (0.5-0.8)**
| Partial match, likely relevant
| "Check Service Health" for calls drop

| **Low (< 0.5)**
| Weak match, probably not relevant
| "Collect Diagnostics" for calls drop
|===

The NLP works by analyzing:

* Alert text: "Number of calls is anomalously low"
* Template name: "Restore Web App Service"
* Template description: (contains keywords about recovery, service, calls)

**Result**: High confidence match → shown first in recommendations

[NOTE]
====
NLP is built into Instana. No external LLM calls needed. Instana uses word embedding and semantic similarity to score templates. This makes it fast, offline-capable, and compliant with data residency requirements.
====

Now we'll trigger both remediation paths by breaking the service.

3. Search for: `❌ LINUX | Web App | Break`

image::aap_break_template.png[Break Template, link="_images/aap_break_template.png", window=blank]

[start=4]
4. Click the template name
5. Click **Launch**

image::aap_launch_button.png[Launch, link="_images/aap_launch_button.png", window=blank]

[start=6]
6. Accept defaults and click **Launch**

This job will SSH to `node2` and stop the `lab-webapp.service` systemd service. The Flask application will stop responding.

image::aap_break_job_executing.png[Break Job Executing, link="_images/aap_break_job_executing.png", window=blank]

[start=7]
7. Wait for the job to complete (about 30-60 seconds)

== Step 5: Observe Instana Alert Firing

Switch to the Instana browser tab and watch your service metrics.

=== Calls Drop to Zero

1. In Instana, navigate to **Services** → `lab-webapp-{guid}`
2. Open the **Analytics** or **Timeline** view
3. Watch the **Calls** metric line drop to zero

image::instana_calls_drop_graph.png[Calls Drop to Zero, link="_images/instana_calls_drop_graph.png", window=blank]

This happens within seconds of the service stopping. The continuous traffic generator on the bastion tries to reach the Flask app and fails.

=== Smart Alert Fires (OPEN)

Wait 1-2 minutes for the alert to evaluate and fire:

1. You'll see an **alert notification** appear in Instana
2. The alert state is **OPEN** (problem detected)
3. The alert will include the metric value (0 calls) and threshold (1 call)

image::instana_alert_open.png[Alert OPEN, link="_images/instana_alert_open.png", window=blank]

[NOTE]
====
The alert takes ~1 minute to fire because Instana's Smart Alert uses a **1-minute evaluation granularity**. It waits for metrics to stay below threshold for the full minute before firing. This prevents false positives from brief, transient glitches.
====

== Exercise 2: Path 1 - Automated EDA Remediation

When the alert fires, the webhook is sent to your EDA listener, which automatically executes the remediation.

=== Verify EDA Received the Webhook

1. SSH to your bastion VM
2. Check the EDA logs:

[source, bash, role="execute"]
----
# View recent EDA activity
ssh bastion "sudo journalctl -u eda -n 20"
----

You should see log entries showing:

* Webhook received from Instana
* Rule matched: `state == "OPEN"`
* Job template triggered: `LINUX | Web App | Restore`

[NOTE]
====
Exact log output depends on your EDA configuration. In the lab, check the systemd journal. In production, check EDA activation logs in the AAP UI.
====

=== Automatic Job Launch in AAP

1. Return to Ansible Automation Platform
2. Navigate to **Automation Execution** → **Jobs**
3. Look for a recent job: `LINUX | Web App | Restore`

image::aap_restore_job_auto_triggered.png[Auto-Triggered Restore Job, link="_images/aap_restore_job_auto_triggered.png", window=blank]

This job was automatically launched by EDA (not by you manually). It will:

* Connect to `node2`
* Start `lab-webapp.service`
* Verify health checks pass

[start=4]
4. Click on the job to view details and **wait for it to complete**

image::aap_restore_job_details.png[Restore Job Details, link="_images/aap_restore_job_details.png", window=blank]

You've completed **Path 1 (automated remediation)**. The entire flow was:

1. Service breaks
2. Instana detects (1 min)
3. Alert fires (immediate)
4. Webhook to EDA (immediate)
5. EDA triggers AAP (immediate)
6. Job executes (~30 sec)
7. **Total time: 2 minutes**

== Understanding the Dual-Path Architecture

=== When to Use Path 1 (Automated EDA)

✅ **Use Path 1 when**:

* Failure mode is well-known and safe (service restart)
* Need fastest possible response (milliseconds matter)
* No compliance requirement for approval
* Intent is full automation with zero human touch

❌ **Don't use Path 1 when**:

* Remediation could have side effects
* Regulatory/governance requires human review
* Multiple remediation options exist (need selection)
* Incident context should inform the decision

=== When to Use Path 2 (Manual Selection)

✅ **Use Path 2 when**:

* Multiple remediation options available
* Need human decision-making
* Compliance requires audit trail
* Learning/training scenario (understanding options)
* Incident context is complex

❌ **Don't use Path 2 when**:

* Need immediate response (seconds matter)
* Failure mode is deterministic (only one right action)
* Manual step would be bottleneck

=== The Instana + AAP Architecture

[source, text]
----
Instana detects incident
         ↓
    ┌────┴────┐
    ↓         ↓
  Path 1    Path 2
  (EDA)    (Manual)
    ↓         ↓
  Auto       Human
 Trigger    Clicks
    ↓         ↓
  AAP API  AAP API
    ↓         ↓
Restore    Restore
----

Both paths call the same AAP job templates. The difference is **trigger mechanism**: webhook (automated) vs. HTTP API call from Instana (manual).

Instana provides **AAP integration credentials** (org + user) that allow it to discover and call job templates. This integration is bidirectional:

* **Instana → AAP**: Discover templates (polling) & execute (API calls)
* **AAP → Instana**: (Optional) Send events/status via webhook
