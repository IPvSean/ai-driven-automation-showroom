= Section 1 Part 1 - Instana Observability and Infrastructure Monitoring

== Objective

In this section, we will explore **IBM Instana**, an enterprise-grade observability platform that provides real-time monitoring, intelligent alerting, and automated incident detection. This section demonstrates how observability platforms integrate with Ansible Automation Platform for intelligent remediation workflows.

Instana continuously monitors your infrastructure and applications, detecting anomalies automatically. When issues occur, it generates intelligent alerts that trigger automated remediation through Event-Driven Ansible, creating a complete closed-loop AIOps workflow.

== What is Instana?

Instana is an AI-powered observability and application performance monitoring (APM) platform that provides:

* **Full-stack observability**: Monitor infrastructure, containers, applications, and synthetic transactions
* **Automated discovery**: Automatically detects and monitors services, dependencies, and infrastructure
* **Intelligent alerting**: Uses machine learning to detect anomalies without manual threshold configuration
* **Native integrations**: Built-in connectors for major platforms including Ansible Automation Platform
* **Closed-loop remediation**: Trigger automated responses through webhooks and API integrations

In this lab, Instana is monitoring a **Flask web application** (`lab-webapp`) running on `node2`. The Instana agent collects metrics about service latency, error rates, throughput (calls), and infrastructure health. When the application stops responding (calls drop to 0), Instana detects this anomaly and sends a webhook alert to Event-Driven Ansible, which triggers an automated remediation workflow.

=== 3. Smart Alerts

Smart Alerts are intelligent, threshold-less alerting that detects when your service behaves abnormally. Unlike traditional alerting (which requires you to manually set thresholds), Instana's Smart Alerts use machine learning to understand normal baseline behavior and alert only when something is actually wrong.

==== Types of Smart Alerts

In this lab, we're using a **Service-level Smart Alert** configured to monitor **Calls (Throughput)** metric:

* **Metric**: Number of calls (HTTP requests per minute)
* **Trigger condition**: `< 1` (less than 1 call per minute = service is down)
* **Evaluation granularity**: 1 minute (evaluates every minute)
* **Scope**: Specific service (`lab-webapp-{{ guid }}`)
* **Channel**: Generic webhook → EDA webhook URL

When the alert fires:
1. **State = OPEN**: Service is down (calls dropped below threshold)
2. **State = CLOSED**: Service recovered (calls restored above threshold)

The webhook payload contains detailed incident information that the EDA rulebook uses to decide on remediation actions.

== Instana Webhook Payload Structure

When a Smart Alert fires, Instana sends a webhook with this structure:

[source, json]
----
{
  "issue": {
    "state": "OPEN",                           // "OPEN" = alert triggered, "CLOSED" = resolved
    "severity": 10,                            // Alert severity level
    "type": "incident",                        // Type of issue
    "metricName": "calls",                     // What metric triggered the alert
    "metric": "0.0",                           // Current value (0 calls = service down)
    "thresholdValue": "1.0",                   // Alert threshold
    "entityLabel": "lab-webapp-ds2nq",        // Service name (matches your INSTANA_SERVICE_NAME)
    "text": "Number of calls is anomalously low",  // Human-readable alert message
    "link": "https://unit0-techzone.../events;eventId=...",  // Link to incident in Instana UI
    "start": 1791404942004,                    // Timestamp when issue started
    "entity": "Service",                       // What type of entity (Service, Application, etc)
    "zone": "not available"                    // Zone info (for service alerts, may be N/A)
  }
}
----

This payload is parsed by the EDA rulebook to:
1. Extract the service name (`entityLabel`)
2. Determine the state (`OPEN` = alert, `CLOSED` = resolved)
3. Trigger appropriate remediation actions
4. Pass context to the AAP workflow

== Two Paths to Remediation

Based on the Instana alert, AAP can take two complementary paths:

=== Path 1: Direct Remediation (Immediate)

When the alert fires, immediately trigger a job template to restore the service:

[source, yaml]
----
- name: "Trigger direct remediation on Instana OPEN alert"
  condition: event.payload.issue.state == "OPEN"
  actions:
    - run_job_template:
        name: "LINUX | Web App | Restore"
        organization: "Default"
----

**Advantages**:
* Fast response time
* Predictable remediation action
* Good for well-known failure modes

**Use case**: Service restart, connection reset, application hang

=== Path 2: AI-Driven Remediation (Intelligent)

Analyze the alert with AI to select the best remediation from multiple options:

[source, yaml]
----
- name: "Trigger AI-driven remediation on Instana OPEN alert"
  condition: event.payload.issue.state == "OPEN"
  actions:
    - run_workflow_template:
        name: "AI-Driven Instana Remediation"
        organization: "Default"
        extra_vars:
          instana_event: "{{ event.payload.issue }}"
          metric_name: "{{ event.payload.issue.metricName }}"
          service_name: "{{ event.payload.issue.entityLabel }}"
----

**Advantages**:
* Intelligent action selection
* Learns from incident patterns
* Can select different remediation based on context
* Opportunity for human approval before execution

**Use case**: Multiple remediation options, complex incidents, critical services requiring approval
